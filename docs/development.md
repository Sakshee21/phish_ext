# Development Guide

## Prerequisites

- Node.js >= 22.6 (`scripts/hash-png.ts` relies on `node --experimental-strip-types`)
- pnpm >= 9
- Python 3 + Playwright (only for the dataset tooling — see `tools/README.md`)

## Setup

```bash
git clone https://github.com/parthsidpara/phish_ext.git
cd phish_ext
pnpm install   # install deps + run wxt prepare (postinstall)
pnpm dev       # start dev mode, opens Chromium with extension loaded
```

## How the pipeline works

1. **Page loaded** — `background.ts` detects navigation via `webNavigation.onCompleted`.
2. **Screenshot** — background calls `tabs.captureVisibleTab` and sends the image to the offscreen document.
3. **pHash** — offscreen document decodes the image and runs the DCT-based perceptual hash (Layer 1).
4. **Visual match** — background compares the hash against each brand's reference hashes
   (primary + `phashByViewport`, picking the closest) within the brand's threshold.
5. **Domain check** — Layer 2. If a visual match is found, background runs
   `checkDomainLegitimacy()`: allowlist (exact or subdomain) → safe; homoglyph /
   Levenshtein lookalike → typosquatting; otherwise → domain mismatch.
6. **Aggregation** — background builds a `DetectionResult{ riskScore, matchedBrand, flaggedElements, reasoning }`
   plus a `comparison` (the real brand's look, for the side-by-side panel). Layer 3's
   text/DOM signals are wired into the verdict; logo template matching is not — see status below.
7. **Warning** — background sends `DETECTED` to the content script, which dispatches to the
   active warning condition (banner / modal / tooltip / icon / progressive) and logs every user action.

## Current status & next steps

**Done:**
- Layer 1 (pHash) — implemented in `src/utils/phash.ts`, computed in the offscreen document, validated via `pnpm test:phash`.
- Layer 2 (domain legitimacy) — implemented and wired into `runPipeline`.
- Pipeline orchestration — screenshot → hash → nearest-brand match → domain check → `DetectionResult` → `DETECTED`.
- Warning layer — four renderers (`banner`, `modal`, `tooltip`, `icon`) + condition switching via the popup (`storage.local['phish_condition']`).
- Progressive Reveal — `behavior-monitor.ts` (dwell timer + cursor-proximity + focus/typing signals; icon → banner+highlight → banner → modal escalation) wired as the `progressive` condition.
- Interaction logging — `shown` / `escalated` / `dismissed` / `proceeded` /
  `went-back` / `left-page`, plus the `approached` / `focused` / `typed`
  engagement micro-events (Progressive Reveal only). Every event carries a
  `visitId` grouping one flagged page-load; `escalated` events record the
  auto/manual trigger. `left-page` is recorded on `pagehide`, so a participant
  who reacts by simply navigating away is counted. Writes are serialized so
  concurrent events (micro-event bursts, `pagehide`, multiple tabs) can't
  overwrite each other.
- Visit grouping & metrics — `utils/visits.ts` groups events by `visitId` and
  derives per-visit metrics (time to react, engagement duration, first-signal
  time, stages reached, escalation/micro-event counts, terminal type); the
  export is a nested `visits` structure (schema v3).
- Study-log viewer — participant-facing page (`/logs.html`, opened from the popup) showing the
  full interaction history with date/type/condition filters, a per-install participant ID, and a
  JSON export (`utils/log-export.ts`) for researchers. Nothing leaves the device except via that export.
  A **Send to study** button uploads the current view straight to the submission site using the
  participant's Google account via `chrome.identity` (needs the `identity` permission + the
  `oauth2.client_id` in `wxt.config.ts`). The site origin is set with the `WXT_SUBMISSION_SITE`
  env var (in `.env`, gitignored); the button is disabled when it's unset.
- Dataset tooling — `tools/generate.sh` captures brands at multiple viewports and writes `brands.json` (see `tools/README.md`).

**Next:**
- Layer 3 — canvas-based logo template matching (`MATCH_LOGOS` in the offscreen worker). The
  text/DOM side of Layer 3 is already wired into the verdict.
- Richer Progressive Reveal evidence — `flaggedElements` already carry CSS selectors, so the
  Stage-2 highlight and per-stage evidence reveal are active; logo template matching would add a
  stronger, viewport-proof signal.

## Warning conditions

The active condition is stored under `phish_condition_assignment`, assigned
once per install (randomly, or via the dev-only popup picker):

| Condition | Behavior |
|---|---|
| Banner | Dismissible strip at the top of the page, non-blocking. |
| Modal | Full-screen interceptor, forces an explicit choice. |
| Tooltip | Warning anchored to the password field. |
| Passive icon | Corner indicator; click to expand the reasoning. |
| Progressive Reveal | Adaptive: passive icon → highlight/banner → modal, escalating as the user hesitates (dwell, cursor proximity to the password field, focus/typing). |

Driver.js (`highlightEvidence` in `utils/driver-highlight.ts`) runs for
Progressive Reveal's on-page evidence and shows the evidence tour once
`flaggedElements` carry CSS selectors (from Layer 3 / visual-similarity flags).

Chromium-only. Development currently targets Chromium.
